## 1. Scope

Read every control on the panel and drive its LEDs, from HARDWARE-SPEC.md, the SDK headers and the allowed FM-1-RE documents:
- **Keys and buttons:** scan the matrix, debounce, and report presses and releases with timestamps; handle several held at once, and say in the design notes what the matrix can and can't tell apart.
- **Encoders:** decode direction and steps reliably at any speed fwtest can produce; optional acceleration, documented.
- **Pot:** read it, filter noise, and report changes with a dead band, without jitter at rest.
- **LEDs:** set each LED's state (and brightness, if the spec allows it).
- **An input layer:** one event queue the rest of the firmware reads (control ID, kind, value, time), with control IDs named after the printed panel labels. Later milestones and other people's engines will build on this API, so keep it small, documented, and stable.
- **A live test screen:** show the state of every control and light the LEDs to match, so the whole panel can be exercised in the app by hand.

The mapping from fwtest's input numbers to the printed labels is emulator-only in the spec: confirm each mapping with your own black-box test before relying on it, and record it.

## 2. Tests

- fwtest input scripts with golden outputs: each key and button, chords, fast and slow encoder turns both ways, the pot swept and held still, every LED; debounce and latency (from input to event, and to LED change) within stated limits, timed exactly per HARNESS.md's rules.
- R-KEY-*, R-ENC-*, R-POT-*, R-LED-*, R-INPUT-* requirements, traced in the record.

## 3. Performance and budgets

- Scanning will cost steady-state instructions. If the M2 budgets don't fit, raise them to M3 budgets in their own small PR first, with headroom you justify. Report what scanning costs per period in the design notes.
